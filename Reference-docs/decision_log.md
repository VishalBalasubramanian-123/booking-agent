Running log of decisions made and bugs found during implementation (mentored sessions), starting 2026-08-27. Newest entries at the bottom of each section. Companion to the other `Reference-docs/*.md` files — those describe the intended design; this one tracks what actually got decided/changed as building hit real questions the original design docs didn't answer.

## Scope decisions (deadline: Sept 14/15, 2026)

- **Bucket 3 deferred.** Owner-decides-with-free-text (e.g. combining tables for an oversized party — see `design_notes_escalation_model.md`) is out of scope for this pass. Only bucket 1 (agent decides alone) and bucket 2 (owner yes/no verification) are being built. Implication: `table_number` always resolves to a single table, no combine-tables logic anywhere.
- **One active table booking per session.** Deliberately simplified from what the schema technically allows (a `session` can have many `reservation` rows). A session may only have one **active** (`pending`/`confirmed`) reservation at a time — a `declined`/`cancelled` prior attempt does *not* block a retry in the same session (session = one continuous conversation, not "one booking attempt ever").
- **Demo interface: the existing CLI loop in `agent.py`**, not a webchat frontend. No polling endpoint or frontend UI will be built for this deadline.
- **Owner notification: a simple internal "owner inbox"** (DB-backed, checked/responded to manually) — no real SMS/Slack integration.
- **`check_KB`: a simple structured/keyword lookup** for allergens/policies — no embeddings/vector RAG for this pass. (`closing_hours` was already pulled out of `check_KB` entirely — see below.) **Superseded 2026-09-07 (see the "Goal changed" entry below) — `check_KB` will be built directly as an embeddings-based semantic-matching tool** (what was scoped as Phase 11/V2 RAG), skipping the keyword-match intermediate version, with an explicit ~3-day budget. Terminology note from that discussion: "semantic matching over stored embeddings" and "a RAG tool" are the same thing here — the retrieval step is identical either way, the agent's own synthesis of whatever `check_KB` returns is the "generation" half, same as it would be with keyword matching. Recommendation given at the time (build the simple version first, to validate the tool-wiring cheaply before adding embeddings complexity) was heard and knowingly overridden, not missed — user's call given the timeline is no longer crunched. Some partially-written keyword-match code (`get_kb_content` in `queries.py`, had a table-name typo and an incomplete query) will be superseded by this, not fixed forward.
- **Build order:** `check_booking` fixes → `cancel_booking` → deterministic bucket-gate function → simple `check_KB` → `reserve_table` → `verification_to_human`/`decision_to_human` + owner inbox → hold-expiry sweep → deploy.
- **`_bucket_gate` design (V1): any allergy/safety mention at all routes to bucket 2, no mild/severe keyword distinction.** Simpler and safer than a keyword-severity split — removes the risk of a real severe case being misclassified as mild by an incomplete keyword list. Pairs with the existing fail-safe-on-ambiguous rule: anything the function doesn't recognize as "no mention" still safely falls to bucket 2, so the function doesn't need to be exhaustive to be safe. Makes `check_KB`'s answer irrelevant to this specific decision (any mention escalates regardless of KB confidence) — so Phase 2 no longer strictly depends on Phase 3. **V2 idea, deliberately not pursued for now:** using an embedding model to distinguish real safety concerns from casual food preferences, to cut down on unnecessary owner pings. Recommendation given: don't build this — a similarity-threshold gate reintroduces the same non-determinism problem "pure LLM judgment" was already rejected for, and the cost asymmetry is bad (a false negative here risks real harm; a false positive just costs the owner a few seconds). Better fix if ping-volume ever becomes a real problem: tighten `system_prompt.md`'s extraction guidance (already done, see below) rather than adding a second judgment layer inside the deterministic gate.
- **Timeline (2026-09-07): V1 stays on the original Sept 14 submission deadline.** Briefly considered extending to Sept 25/30 to also fit multi-restaurant support and full RAG into the initial submission — walked back after laying out the actual scope of both (see below): 8 days isn't comfortable for either one alone, let alone both, on top of `reserve_table` and everything after it still being unbuilt. Final call: V1 (current scope — single restaurant, simple `check_KB`, bucket 1+2 only) ships for the Sept 14 submission as originally planned; multi-restaurant support and full RAG become V2 work continuing afterward, with Sept 30 as a soft target for that follow-on work, not the submission itself.
- **Multi-restaurant support deferred to V2.** Scoped out after laying out the real size of it: every restaurant-scoped query (`get_tables`, `get_closing_time`, possibly others) would need a `restaurant_id` filter added, `check_availability`'s public signature (and all 12 of its tests) would change, and there's currently no mechanism at all for establishing "which restaurant is this conversation for" (no restaurant_id anywhere in `agent.py`, and `customer`/`session` have no restaurant_id column either — open question for V2 on whether customer identity is global or per-restaurant). V1 stays single-restaurant, but the restaurant name is pulled from `restaurant_info` into the prompt at agent-startup time instead of being hardcoded prose — see below.
- **Goal changed (2026-09-07): the hackathon deadline pressure is off, target shifted to "genuinely well-engineered, portfolio-quality" by end of Sept / Oct 5, with V2 included.** Explicitly *not* aiming for true production hardening (no rate limiting, no multi-env CI/CD, no formal load testing, no compliance work — none of that matters without real public traffic). The subset that *is* in scope, because it demonstrates real engineering skill without being disproportionately expensive:
  1. **Concurrency correctness on the core booking flow** — the "one active reservation per session" rule is currently only an app-level check-then-insert, which races under concurrent requests. Needs a DB-level constraint (or transaction), designed into `reserve_table` from the start, not retrofitted after.
  2. **Real input validation/error handling at every tool boundary**, same reasoning — build it in as each function is written.
  3. **Evals for the LLM-extraction layer** — a small set of scripted example conversations (allergy edge cases, tool selection, out-of-scope questions) run through the real agent, checking it called the right tool with the right extracted arguments. Different from the existing unit tests, which only prove the deterministic Python is correct.
  4. **Basic structured observability** — log every tool call (action, args, result, latency) from `tools_lambda/handler.py`; CloudWatch Logs Insights is enough, no dashboard product needed.
  5. **Real IaC** (SAM or CDK) for the two Lambdas + IAM + the EventBridge schedule, instead of manual console deploys.
  6. **A proper README/architecture writeup** at the end, tying this decision log together for an audience.
  - Revised estimate: V1 remaining (~7-12 days) + V2/multi-restaurant+RAG (~5-9 days) + this pruned list, woven into the work rather than done as a separate pass (~5-9 days) ≈ 17-30 days, against a 23-28 day window (today to Sept 30/Oct 5). Plausible, not comfortable.
- **Eval tooling: RAGAS for RAG (settled), agent tool-calling eval tool not yet chosen.** RAGAS is the right fit for evaluating Phase 11's RAG pipeline specifically (faithfulness/context-relevancy metrics against retrieved content) — committed, to be wired in once real retrieval exists. For agent tool-calling eval, candidates raised: DeepEval, AgentBench, LangGraph. Recommendation given (not yet acted on): start with a lightweight hand-rolled `pytest` harness first — scripted conversations through the real agent, asserting on which tool got called with which extracted arguments — since the user is new to evals entirely and this needs zero new dependencies, reusing the testing pattern already used all session. Treat a dedicated framework (DeepEval most likely, given its pytest integration) as an optional upgrade layered on *after* basic coverage exists, not a blocker for getting eval coverage at all. Also flagged: both RAGAS and typical agent-eval frameworks use an LLM to judge outputs (cost + some non-determinism in the eval itself), and DeepEval's current depth of agent/tool-calling-specific metrics wasn't verified against live docs — check before committing.

## Architecture decisions

- **`check_availability` occupancy:** defaults to 90 minutes (`DEFAULT_OCCUPANCY_TIME`), overridable via an optional `stay_minutes` param when the guest specifies how long they're staying.
- **Restaurant hours live as 4 columns on `restaurant_info`** (`weekday_opening_time`, `weekday_closing_time`, `weekend_opening_time`, `weekend_closing_time`), not a separate table. Reasoning: it's a true 1:1 relationship (one restaurant → one weekday schedule + one weekend schedule), not 1:many, so the "FK on the many side" pattern used elsewhere (`table_unavailability`, `reservation_tables_booking`) doesn't apply — a separate table would just add an unneeded join. Trade-off accepted: true per-day-of-week granularity later would need a schema migration under this approach.
  - **Not yet applied to `db/schema.sql`** — only given as a standalone `ALTER TABLE` script. Check whether it was actually run against live Supabase, and update `schema.sql`'s `restaurant_info` definition to match either way (currently out of sync with what `get_closing_time` assumes exists).
- **`closing_hours` bypasses `check_KB` entirely** — `check_availability` calls `get_closing_time(date)` (in `shared/queries.py`) directly, not through the KB/RAG layer. Reasoning: closing time is a deterministic, structured value needed for a correctness-critical comparison; routing it through RAG would mean parsing a value out of a free-text answer, which violates "the LLM proposes, the system disposes" (`idea.md`). `check_KB` stays reserved for genuinely open-ended questions (menu, policies) and is untouched/deferred.
- **Guest channel is a webchat session that stays open** until the booking resolves (confirmed/declined) — not SMS/async push.
- **Status polling must not go through the LLM/agent.** Checking "is this row still pending" is a mechanical DB read, not a language task — routing it through Bedrock on a timer would be costly, add latency, and violates "LLM proposes, system disposes" one level up (even the choice of *whether* to use the LLM follows that rule). The frontend should poll a lightweight, non-agent endpoint on a timer; `check_booking` itself stays LLM-tool-callable for when the guest asks mid-conversation, using the same underlying read logic.
- **`check_booking` always returns the real status, including `'pending'`** — never a fabricated confirmation. Translating `'pending'` into guest-friendly phrasing ("still checking with the team") belongs in `system_prompt.md`, not in the tool's return value.
- **`session` is a conversation container, not "a booking."** A session can hold a whole back-and-forth (Q&A, multiple booking attempts) — a `reservation.session_id` just records which conversation a booking happened during.
- **Session lifecycle is currently unbuilt** — `session_id` is only ever *read* (never created) anywhere in the codebase today. Given the CLI-loop demo scope, the plan is: create the `session` row once at script start (`if __name__ == "__main__":`), session ends when the guest types `"exit"`. No inactivity timers or webhook-based session-end needed given the single-process demo scope.

## `check_availability` — bugs found and fixed (now fully tested, 12 passing tests in `tests/test_booking.py`)

1. Maintenance-window branch was using a generator expression (or later, `.append([...])`) instead of `.extend([...])`, and later mis-shaped the `window` field — fixed to `results.extend([...])` with each maintenance row trimmed to `{"table", "available", "reason", "window": [start, end]}` (window values parsed via `datetime.fromisoformat`).
2. `get_closing_time` had a stray double `datetime.combine(...)` call around an already-correct `datetime` — fixed to return the already-combined value directly.
3. Lookahead loop (`else` branch, "look ahead up to 2 days") had two date-mismatch bugs: `get_closing_time(date)` was using the *original* date instead of `next_date`, and `_find_next_free_start(requested_start, ...)` was anchored to the original date instead of `datetime.combine(next_date, time)` — both fixed. The second bug meant the lookahead conflict check was silently non-functional (comparing candidates on one day against bookings on a different day, which can never overlap).
4. Maintenance wasn't being re-checked for lookahead days at all — added `get_maintenance_window(table_id, next_date, time)` inside the lookahead loop, `continue` if found.

## `check_booking` — fixed as of 2026-09-05/06

Issues found and resolved, across a few iterations:
- `get_booking_status` returning a **list** but being indexed like a dict — fixed to `current_status[0][...]`, guarded by `if current_status:`/`else: return None` for the not-found case.
- `occupancy_end_time` (a full `TIMESTAMP`) was parsed with a bare-time `strptime` format, then wrapped in a redundant/type-wrong `time.fromisoformat()`, and — the root cause under both — `datetime.time` objects don't support subtraction at all. Fixed by using `datetime.fromisoformat(occupancy_end_time) - datetime.combine(date, time)` — full `datetime`s on both sides, correct subtraction order (end minus start) for a positive `timedelta`.
- An intermediate rewrite introduced a broken list-comprehension (`for status in current_status if status else None` — references the loop variable before it's bound, `NameError`; also would've returned a list of `None`s since `response` was built from `.append()`'s return value, not the actual data) — reverted to a plain `if current_status: ... else: return None`.
- **Still open, not yet fixed:** `booking_id` type mismatch (`agent.py` types it `str`, `reservation_id` is `INT`).

**Related schema decision:** `reservation.occupancy_end_time` is now `NOT NULL` (in both live Supabase and `db/schema.sql`), not left null until confirmation. Reasoning: `get_existing_bookings` includes *pending-but-on-hold* rows in its conflict check (that's what makes the "table hold on escalation" non-negotiable actually work — a held table must show as occupied to other guests, not just a confirmed one). If `occupancy_end_time` were only set on confirmation, a pending hold would either crash `get_existing_bookings` (parsing `NULL`) or — if that crash were papered over — silently fail to block a double-booking during the hold window. So `occupancy_end_time` must be computed and written at row-creation time (whatever the initial status), which is now a locked-in requirement for `reserve_table`'s insert logic.

## `cancel_booking` — bugs found and fixed (2026-09-06)

- `update_status` (`shared/queries.py`) filtered `.eq("session_id", session_id).eq("session_id", booking_id)` — both `.eq()` calls on the same column, meaning the update could never match a real row (required `session_id` to equal two different values at once). Fixed to `.eq("reservation_id", booking_id)` for the second filter.
- Missing "booking not found" guard caused a `TypeError` when `check_booking` returned `None` — the original `if check_status and ...` correctly short-circuited without crashing *on that line*, but execution then fell through to `check_status["session_id"]` a few lines later, which crashed on `None`.
- An attempted fix (`if not check_status and check_status["status"]...`) made things worse: it crashes immediately on `None` instead (since `not None` is `True`, forcing `and` to evaluate the right side), *and* it made the status-blocking check permanently unreachable — `not check_status` is `False` for *any* existing booking regardless of status, so `'pending'`/`'declined'`/`'cancelled'` bookings would all get silently cancelled too, not just `'confirmed'` ones.
- **Fixed** by splitting into two separate, sequential checks — `if check_status is None: return ...` first, *then* `if check_status["status"].lower() in [...]: return ...` — rather than trying to combine "does it exist" and "what does its status allow" into one boolean expression.
- F-string using double quotes nested inside a double-quoted string (`f"...{x["key"]}..."`) — only valid on Python 3.12+ (PEP 701); works in this local `.venv` (3.14) but could be a hard `SyntaxError` on an older Lambda runtime. Fixed to single quotes inside.

**Design decision confirmed (not a bug):** cancellation blocks `'pending'` bookings, not just `'declined'`/`'cancelled'`. Reasoning: given bucket 3 is deferred, `'pending'` can currently only mean bucket-2 verification is in flight — the owner has already been pinged and may be actively deciding. Letting the guest cancel mid-flight would confuse the owner (responding to a request that's already gone) and risks a race against `decision_to_human` writing a result to the same row. Only a `'confirmed'` booking is safe to let the guest cancel themselves.

## `reserve_table` — design decisions so far (not yet implemented)

- Needs a `session_id` parameter added to its signature (currently missing).
- First step, before anything else: call `get_active_reservation_for_session(session_id)` — a new query function, `.eq("session_id", session_id)` + `.in_("confirmed_declined", ["pending", "confirmed"])` — and block the attempt if it finds one.
- Blocked-attempt response shape (chosen): return both a message *and* the existing booking's details, not just a bare rejection —
  ```python
  {
      "message": "You already have an active reservation for this session.",
      "existing_booking": {"date": ..., "time": ..., "status": ...},
  }
  ```
  so the guest doesn't have to separately ask `check_booking` to see what they already have. Table number intentionally left out of this response for now (would need an extra join) — not essential, can add later.
- Still open / not yet decided: customer lookup key (phone? email? some combination? — flagged as open in `booking_flow_design.md` too), whether `reserve_table` re-verifies availability itself before inserting (race condition since time may have passed since the guest's original `check_availability` call), hold TTL sourcing now that bucket 3 is deferred (bucket 1 = no hold, straight to `confirmed`; bucket 2 = 5-minute hold — the 15-20 minute bucket-3 window is moot for now).
